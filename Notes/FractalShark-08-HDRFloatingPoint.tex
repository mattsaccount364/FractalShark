\section{HDR Floating-Point Representation}
\label{sec:hdr-float}

Deep-zoom Mandelbrot rendering must represent pixel offsets far below the
smallest nonzero native floating-point value. For example, an offset of
$2^{-2000}$ is meaningful in a sufficiently deep view, although it underflows
to zero in IEEE~754 double precision. Computing every pixel with arbitrary
precision would retain that offset but repeat expensive work across the image.
The desired representation instead combines a wide exponent range with the
modest significand precision needed for per-pixel perturbation.

To address this gap, the implementation employs a custom \emph{high dynamic range (HDR)}
floating-point representation that explicitly separates scale and precision
(\cref{fig:type-hierarchy}).
The representation extends range while retaining the precision of its selected
mantissa type; it does not manufacture additional significant bits.

\subsection{Decoupling scale and precision}

In standard IEEE floating-point arithmetic, each finite nonzero value has a
significand multiplied by a power of two. The significand precision is fixed:
a normal float has 24 significant binary digits and a normal double has 53,
regardless of magnitude. Absolute spacing grows with magnitude, while relative
spacing remains approximately constant. Subnormal values near underflow have
fewer significant digits. The limitation addressed here is the finite exponent
range, rather than a loss of normal-number significand bits at large magnitudes.

The HDR representation instead stores values in the form
\begin{equation}
x = m \cdot 2^{e},
\end{equation}
where:
\begin{itemize}
\item \(m\) is a fixed-precision mantissa stored in standard floating-point or
      multi-component expansion format, and
\item \(e\) is an explicitly managed integer exponent.
\end{itemize}

By storing the exponent separately, the mantissa can remain near unit magnitude
even when the represented number is extremely small. For example,
$x=1.5\cdot2^{-2000}$ stores the ordinary mantissa~1.5 and the integer
exponent~$-2000$. The available exponent range is finite, but substantially wider
than the native float or double range. Rounding, cancellation, and insufficient
mantissa precision remain possible.

\subsection{Normalization and arithmetic}

Reduced nonzero scalar values use a mantissa with $1\le |m|<2$ for the native
mantissa types. Multiplication or addition may temporarily leave that range;
\code{Reduce()} transfers the mantissa's binary scale into the explicit
exponent. Performance-sensitive code can delay reduction, so normalization is
a required property at designated operation and comparison boundaries rather
than a claim that every intermediate is immediately normalized. Zero has a
separate representation and does not satisfy the nonzero invariant.

Arithmetic operations are performed as follows:
\begin{itemize}
\item \textbf{Multiplication} combines mantissas and adds exponents.
\item \textbf{Addition and subtraction} align exponents explicitly before
      operating on mantissas.
\item \textbf{Renormalization} transfers powers of two between the mantissa and
      exponent without changing the represented value, apart from arithmetic
      rounding already incurred.
\end{itemize}

Because mantissas are stored using fixed-precision types, these operations map
naturally to GPU hardware while avoiding the overhead of general-purpose
arbitrary-precision arithmetic.

\paragraph{Worked exponent alignment.}
Let $x=1.5\cdot2^{-2000}$ and $y=1.25\cdot2^{-2002}$. Addition first uses the
larger exponent:
\[
x+y=(1.5+1.25\cdot2^{-2})2^{-2000}
    =1.8125\cdot2^{-2000}.
\]
All mantissa operations are ordinary arithmetic on values near~1; constructing
the unscaled numbers in double precision would have lost both inputs. Their
product is
\[
xy=(1.5\cdot1.25)2^{-4002}=1.875\cdot2^{-4002}.
\]
For a product requiring normalization,
$(1.5\cdot2^{-2000})^2=2.25\cdot2^{-4000}
=1.125\cdot2^{-3999}$. Dividing the mantissa by~2 therefore increases the
stored exponent by~1. Conversely, adding a contribution much smaller than one
mantissa unit in the last place can still round it away; a wider exponent alone
does not prevent that loss.

\subsection{HDR complex numbers}

Mandelbrot iteration operates on complex numbers. In the HDR formulation, each
complex value
\[
z = x + i y
\]
can be represented as two independent HDR scalars. The implementation also uses
\code{HDRFloatComplex<SubType>}, which stores two mantissas with one shared
integer exponent:
\[
z=(m_x+i m_y)2^e.
\]
Construction aligns the component exponents to the larger one, and reduction
uses the larger component scale. The smaller component need not have a
unit-sized mantissa. For example,
$x=1.5\cdot2^{-2000}$ and $y=1.25\cdot2^{-2002}$ become
$z=(1.5+0.3125i)2^{-2000}$. Sharing an exponent reduces storage and alignment
work, but an extreme ratio between components can still underflow the smaller
mantissa. Independent scalar components and shared-exponent complex values
therefore have different representational tradeoffs.

Both forms support magnitudes beyond native exponent limits. Their phase and
magnitude accuracy remain limited by the selected mantissa arithmetic.

\subsection{Role of HDR in perturbation and reference orbits}

The HDR representation plays a complementary role to perturbation
(\cref{sec:perturbation-concept}).  It extends range, not significand precision.
The application-authoritative CPU recurrence uses MPIR, and the CUDA
reference-orbit recurrence uses fixed-width \code{HpSharkFloat}.  Both emit
reduced HDR samples for downstream work.

HDR arithmetic is used primarily for:
\begin{itemize}
\item storing reduced reference-orbit samples and parameters,
\item perturbation and linear-approximation arithmetic whose values require wide
      range but only the selected mantissa precision, and
\item GPU periodicity, escape, radius, and derivative calculations around the
      \code{HpSharkFloat} orbit state.
\end{itemize}

HDR therefore enables the mixed-precision structure used by perturbation
rendering; it does not replace the MPIR or \code{HpSharkFloat} recurrence.

\subsection{Advantages over conventional representations}

Compared to standard floating-point formats, HDR arithmetic offers:
\begin{itemize}
\item substantially increased dynamic range,
\item the selected mantissa precision across that extended range, and
\item explicit normalization and exponent alignment.
\end{itemize}

Compared to arbitrary-precision libraries, it avoids dynamic memory allocation,
irregular control flow, and large per-operation overheads, making it well suited
for parallel execution on GPUs.

\subsection{Choosing range and precision independently}

HDR addresses values that would overflow or underflow a native type. The
multi-component types in \cref{sec:extended-precision-types} address a different
problem: retaining more significant digits when ordinary mantissa precision is
insufficient. Combining the two mechanisms supplies both range and precision
without repeating arbitrary-precision reference calculations for every pixel.
