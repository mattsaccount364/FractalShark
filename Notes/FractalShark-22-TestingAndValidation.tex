\section{Testing and Validation}
\label{sec:testing}
%% ===================================================================

A rendering failure can originate in arithmetic, coordinate conversion,
approximation, coloring, or file output. Validation therefore checks intermediate
contracts as well as final images. Two standalone runners cover complementary
layers: \code{FractalSharkTest} owns CPU utility tests and render regressions,
including explicitly selected CUDA cases, while \code{HpSharkFloatTest} exercises
the high-precision GPU arithmetic engine. Passing one layer does not establish
correctness of every other layer.

\subsection{Render regressions}
\label{subsec:crummytest}

Render regression coverage formerly exposed through the \code{CrummyTest} GUI
actions now belongs to the standalone \code{FractalSharkTest} runner. The old name
is historical, rather than a current menu command. Render cases cover selected
algorithm, view, iteration-width, compression, and save/load combinations;
they do not blindly run every experimental mode.

A fixture calls \code{Drain()} before direct \code{CalcFractal(true)} so the
authoritative CPU iteration buffer is current
(\cref{subsec:two-render-paths}). PNG output uses \code{SaveCurrentFractal} and
waits for save completion before examining the file. GPU cases require
\code{--use-gpu}; View10, View27, billion-element stress cases, and documented
incomplete modes remain disabled in routine runs.

\paragraph{What a golden comparison measures.}
A render golden records the expected decoded RGBA16 image for an established
fixture. Changing DEFLATE compression can change the file bytes while leaving
every decoded channel unchanged. Consequently, render checksums cover decoded
pixels, whereas encoder tests separately verify compression and container
integrity. A successful build alone does not exercise either contract.

For example, changing a pixel's red channel from $1000$ to $1001$ must change
its decoded-image checksum, even if an 8-bit preview displays the same color.
Re-encoding the unchanged pixels with a different valid Huffman table need not
change that checksum. Golden updates therefore require reviewing pixel changes;
they must not be used simply to dismiss a failing comparison. The user appendix
describes the update workflow in \cref{sec:render-regression-tests}.

\subsection{HpSharkFloatTest (GPU arithmetic)}
\label{subsec:hpsharkfloattest}

\code{HpSharkFloatTest} is a standalone CUDA executable (in
\code{HpSharkFloatTest/}) that validates the GPU high-precision
reference-orbit implementation described in \cref{subsec:ref-orbit-gpu}.
Its sole operator is \code{ReferenceOrbit2}, which exercises the complete
fused v2 recurrence.

Each vector is validated through complementary comparisons:

\begin{enumerate}
  \item \textbf{GPU vs.\ MPIR.}  The fused GPU result is converted to
        MPIR values and compared with the same recurrence evaluated in
        arbitrary-precision arithmetic. MPIR supplies the authoritative finite-
        precision reference for this comparison; it is not an exact-real oracle.
  \item \textbf{CPU oracle vs.\ MPIR.}  The CPU
        \code{ReferenceReferenceOrbit2} implementation uses the
        \code{HpSharkFloat} representation and is independently checked
        against MPIR.
  \item \textbf{Pipeline checksums.}  Deterministic host and device
        checksums compare corresponding fused-stage boundaries and identify
        the first stage at which their intermediate representations diverge.
\end{enumerate}

\noindent
When a test fails, the checksum-guided debugging infrastructure
(\cref{sec:checksums}) reduces the mismatch to a targeted fused pipeline
stage.  Hardcoded and generated vectors cover signs, zero values,
carry/borrow behavior, alignment shifts, and fused-stage bounds.  The
Newton--Raphson cases use the same Ref2 engine to exercise first-derivative
and checkpoint-resume paths.  Performance benchmarks exercise the full
reference-orbit pipeline at three zoom depths: View~5
(${\sim}16{,}000$ iterations), View~30 (${\sim}670{,}000$ iterations), and
View~32 (${\sim}30{,}000{,}000$ iterations).

\subsection{FractalSharkTest (utilities and integration)}
\label{subsec:fractalsharktest}

\code{FractalSharkTest} (in \code{FractalSharkTest/}) is a standalone
test executable that validates fundamental data types, numerical helpers,
shared GUI state, reference and approximation storage, save transactions, and
render integration. CPU cases run without CUDA hardware; CUDA cases are selected
with \code{--use-gpu}.  It uses a lightweight
assertion-based framework (\code{TEST}, \code{ASSERT\_EQ},
\code{ASSERT\_NEAR}) and covers:

\begin{itemize}
  \item \code{HDRFloat<T>} arithmetic and normalization
        (\cref{sec:hdr-float}).
  \item \code{HDRFloatComplex} operations (complex multiply, add,
        magnitude).
  \item \code{HighPrecision} string parsing and round-trip conversion.
  \item \code{PointZoomBBConverter} coordinate transforms
        (\cref{subsec:coordinates}).
  \item BLA and LA coefficients, evaluation, parameter handling, and storage.
  \item Save transactions, PNG output, and current-frame recoloring.
  \item Render cases and decoded-image golden checks.
  \item MT9 exact-product oracles, guard limbs, handoff and lifetime checks,
        recurrence precision, Auto selection, compression, and Imagina interchange.
\end{itemize}

\paragraph{Selecting a useful check.}
List tests before choosing a narrow filter; multiple filters select the union of
matching names. For example, the following commands list the catalog and select
HDR arithmetic tests on Windows:
\begin{lstlisting}[language={}]
Debug\FractalSharkTest.exe --list-tests
Debug\FractalSharkTest.exe --filter "*HDRFloat*"
\end{lstlisting}
The portable Linux runner is
\code{./build-debug/FractalSharkTest/FractalSharkTest}. GPU arithmetic validation
requires real CUDA hardware; it is not implied by a CPU-only CI run. Focused
PNG checks are documented in \cref{subsec:png-validation}. Large full-suite runs
can take substantially longer than individual utility cases.

\paragraph{MT9 arithmetic and performance fixtures.}
The \code{RefOrbitKaratsuba\_*} cases compare split products against an
independent \code{mpz\_mul} oracle over every stored input limb. Recurrence
tests apply ordinary full-precision MPIR addition and subtraction after those
oracle products. Product benchmarks and complete-orbit benchmarks are separate:
the latter include sequential recurrence, sample publication, derivative
bookkeeping, and worker startup/teardown. The complete-orbit workload uses
$c=-0.1+0.1i$ and suppresses periodicity termination in benchmark mode.
Each fixture measures 16,384 iterations at 16,384, 33,344, or 100,096 bits;
\code{FRACTALSHARK\_REF\_ORBIT\_PROFILE\_ITERATIONS} can increase that count.
For example:
\begin{lstlisting}[language={}]
Release\FractalSharkTest.exe --filter "RefOrbitKaratsuba_*"
Release\FractalSharkTest.exe --filter "RefOrbitKaratsuba_Profile*"
\end{lstlisting}
Paired Release measurements alternate baseline and candidate order and retain
MT3 as a control. Timing results describe the tested machine and workload,
not a hardware-independent speedup or an end-to-end accuracy certificate.

\paragraph{Dynamic-precision validation.}
The \code{RefOrbit\allowbreak DynamicPrecision\_*} cases exercise the optional strategy in
\cref{subsec:ref-orbit-dynamic-precision}. They provide evidence for the
implementation's arithmetic hypotheses and integration behavior; the enclosure
and accepted-sample arguments are established separately by the derivation.
\begin{itemize}
  \item \code{Local\allowbreak RoundingBounds}, \code{Combined\allowbreak StepBounds},
        \code{Bound\allowbreak Arithmetic}, and \code{Finite\allowbreak Recurrence} check primitive
        bounds, the complete update against exact dyadic arithmetic, and outward
        disk propagation against wide MPIR calculations. Invalid and
        out-of-range bounds must propagate to rejection.
  \item \code{Conversion\allowbreak Certificates} covers strict conversion-bin gaps,
        signs, real-axis zero, and unsupported native exponents.
        \code{ReducedOrbit\allowbreak MatchesOracle} compares successful reduced attempts
        with fixed MT9 and a higher-precision oracle.
  \item \code{PrecisionRestoration\allowbreak AndDerivativeReset} checks that restoring
        capacity preserves the error already incurred and that the derivative
        recovers after cancellation. \code{NearReturn\allowbreak OperandScale} covers the
        small-result/large-operand precision regression.
  \item \code{Fallback\allowbreak MatchesFixed} and \code{Structured\allowbreak DeepFallback} cover
        rejection and restart. \code{StartupStorage\allowbreak AndPeriodicity},
        \code{Active\allowbreak Cancellation}, \code{ManualMenu\allowbreak AndAutoExclusion}, and
        \code{RenderAnd\allowbreak CompressionRoundtrip} cover publication, cancellation,
        selection, rendering, and Imagina interchange.
\end{itemize}
The names above omit the common \code{RefOrbit\allowbreak DynamicPrecision\_} prefix.
The existing \code{ManualMenu\allowbreak AndAutoExclusion} case encodes the
earlier manual-only selection policy; its Auto assertions require alignment
with the current dynamic-MT9 dispatch before they validate that policy.
For example, the existing focused Windows selection is:
\begin{lstlisting}[language={}]
Debug\FractalSharkTest.exe --filter "RefOrbitDynamicPrecision_*"
\end{lstlisting}
The selection also includes three growing-derivative profiling fixtures.
Their sample comparisons and precision statistics complement the correctness
fixtures; elapsed times do not establish a universal speedup. Agreement on
tested inputs does not replace the enclosure proof or extend its certificate
to compression and final-image arithmetic.

The tiered allocation strategy introduced earlier in this chapter addresses one aspect of memory
pressure.  The next chapter examines a complementary mechanism---disk-backed
growable vectors---that manages the large reference-orbit buffers whose size
can exceed available physical memory.
